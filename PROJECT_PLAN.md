## 4. План на 3 участников

### 4.1. Принципы параллельной работы

1. **Contract-first**: в первый день фиксируются колонки, таблицы, пути, формат выходных файлов и сигнатуры функций.
2. **Sample-first**: A делает sample-выборку и схему SQLite в день 0–1.
3. **Fixtures**: B и C работают на sample/фикстурах, не ждут полный датасет.
4. **Output contract**: B отдаёт результаты в согласованные JSON/CSV, C подхватывает их.
5. **Data access abstraction**: C использует `data_access.py`/`db.py`, чтобы не зависеть от реализации A.
6. **Feature branches**: A, B и C работают в отдельных ветках; merge в `main` не реже раза в 2 дня.
7. **Cross-review**: A ревьюит C, B — A, C — B.
8. **Daily standup 15 минут** и 2 глубоких sync, чтобы не тратить время на встречи.
9. **Backlog для простоя**: README, docstrings, тесты, проверка рубрики, подготовка слайдов, проверка SQL.

Если дедлайн короче 10 дней:

- сжимать дни 1–5;
- сохранять три параллельных потока;
- сохранять два sync;
- не переносить отчёт и презентацию на последний день.

Если дедлайн длиннее:

- добавить buffer;
- optional-расширения делать только после закрытия обязательных пунктов.

### 4.4. Механика «никто не ждёт другого»

- **A не блокирует B и C**: sample и схема появляются в день 0–1; B и C работают на sample.
- **B не блокирует C**: C использует согласованные `outputs/*.json|csv`; до готовности B — фикстуры.
- **C не блокирует A и B**: дашборд читает данные через `data_access.py`/`db.py`; до готовности A — CSV/Parquet-заглушка.
- **Отчёт не оставляется на конец**: каждый пишет свой раздел с дня 7, C только собирает.
- **Ежедневный standup 15 минут** и два глубоких sync.
- **Merge в `main` не реже раза в 2 дня**.
- **Перекрёстное ревью**: A ревьюит C, B — A, C — B.
- **Backlog для простоя**: README, docstrings, тесты, проверка рубрики, подготовка слайдов, проверка SQL.

### 4.6. Риски и меры

| Риск | Мера |
|---|---|
| Данных меньше 500 тыс. строк / 200 МБ | A проверяет в день 0; при необходимости добавляет смежные датасеты OWID или согласует исключение |
| Нет готовых `region`/`category` | Создать производные поля и задокументировать |
| Дашборд не сходится с данными | Работать через `data_access.py`/`db.py` и фикстуры; интеграция на дне 6 |
| SQLite не поддерживает нужные оконные функции | Проверить версию SQLite; при необходимости использовать CTE/подзапросы или PostgreSQL |
| Сезонная декомпозиция требует `statsmodels` | Заранее добавить в `requirements.txt` |
| Кто-то перегружен | Перераспределить визуализации/документацию; ежедневный standup |
| Дедлайн близко | Freeze за 4 дня; отчёт и презентация не позже дня 8; buffer на день 10 |
| Большой объём данных замедляет анализ | Использовать Parquet, нужные колонки, агрегации, sample для разработки |
| Утечка данных в прогнозе | Только time-based split; train до test; без перемешивания |

## 6. Прогнозирование: обязательное сравнение

### 6.1. Модели

| Роль | Модель | Комментарий |
|---|---|---|
| Baseline 1 | Naive | Последнее известное значение |
| Baseline 2 | Seasonal naive | Значение с лагом 7 дней или 7 дней назад |
| Подход 1 | Moving average | Скользящее среднее 7/14/28 дней |
| Подход 2 | Linear Regression | Временные и/или лаговые признаки |

Допустимо добавить другие модели, но только после обязательных.

### 6.2. Метрики

- MAE — основная обязательная метрика;
- RMSE — опционально;
- время выполнения;
- потребление памяти;
- таблица сравнения в отчёте.

### 6.3. Защита от утечки

- только time-based split;
- train — более ранний период;
- test — более поздний период;
- без случайного перемешивания;
- признаки не используют будущие данные;
- лаги строятся только из прошлого.
